# near-tla conformance

This crate checks the model in `../modules/` against nearcore. It runs generic probe contracts in
[near-contract-sim](https://github.com/near/near-contract-sim), which executes receipts with
nearcore's own `Runtime::apply`. Each transaction runs at every point of a prepaid-gas grid, and
every receipt is compared with what the model predicts at the same point:

- the receipt status: ok, failed, out of gas, or not created;
- the gas attached to each function call;
- the window edges, i.e. the prepaid values at which the outcome changes.

A flow can go on after its transaction: further transactions at their own gas, or the timeout
of a parked yield (`after`, see [Flow specs](#flow-specs-toml)). That is how the yield/resume
flows run; see [Async patterns](#async-patterns-joint-promises-and-yieldresume).

The crate also has a calibration tool. It measures a contract's burn per method and path, and
writes them as a TLA+ `GasBurn` / `GasCall` table with a provenance header.
`../modules/CalibStd.tla` (standard FT and wNEAR) is generated this way. With `--stor` it
measures the storage bytes each method and path adds instead, for `OStorKey`
([Storage bytes](#storage-bytes)); `../modules/StorStd.tla` is generated that way.

This is a standalone crate. It is outside any workspace and CI does not build it, because the sim
is a git dependency.

## Setup

### Fetching the sim

near-contract-sim is a private repository, so cargo has to fetch it over git with credentials.
The following works with the GitHub CLI signed in. It passes the token through a credential
helper for one command only, and never writes it to a file or remote URL:

```sh
export CARGO_TARGET_DIR=~/.targets/near-tla   # any directory; one per checkout is fine
CARGO_NET_GIT_FETCH_WITH_CLI=true \
GIT_CONFIG_COUNT=2 \
GIT_CONFIG_KEY_0=credential.helper GIT_CONFIG_VALUE_0= \
GIT_CONFIG_KEY_1=credential.helper \
GIT_CONFIG_VALUE_1='!f() { echo username=x-access-token; echo "password=$(gh auth token)"; }; f' \
cargo fetch
```

After the first fetch, cargo builds offline from its git cache.

### Using a local sim checkout instead

Add this to `Cargo.toml` (do not commit it):

```toml
[patch."https://github.com/near/near-contract-sim"]
near-contract-sim = { path = "../../near-contract-sim" }   # your checkout, at the pinned rev
```

Check that the checkout is at the rev in the table above. The provenance check reads the rev
from `Cargo.lock`, so a patched build at a different rev reports the wrong rev.

### The probe contracts

The `.wasm` files in `probes/res/` are committed with their hashes, so the suite runs without a
wasm toolchain. `probe_wasm` refuses a file whose hash is not in `SHA256SUMS`. To rebuild them:

```sh
cd probes && ./build.sh          # builds, copies to res/, rewrites res/SHA256SUMS
cd probes && ./build.sh --check  # rebuilds and verifies against SHA256SUMS
```

`build.sh` runs `cargo build --target wasm32-unknown-unknown --release` with `--cfg near`, as
`cargo near build` does, and the 1.95.0 default wasm features (bulk memory and sign extension
are fine at protocol 88). It remaps every local path prefix (`--remap-path-prefix`) and strips
symbols (`-C link-arg=-s`), so the build is reproducible and the wasm carries no local paths.
There is no wasm-opt pass.

`--cfg near` matters: without it near-sdk 5.29.1 (through near-sdk-env) uses pure-Rust
fallbacks "not for on-chain use", and `env::panic_str` becomes a bare wasm trap (`unreachable`)
instead of the `panic_utf8` host call. With it, a probe's panic shows its message
(`GuestPanic`), and burns are those of an on-chain build.

## Running

All commands run from `conformance/`, with `CARGO_TARGET_DIR` set as above. Tests run one at a
time (`.cargo/config.toml` sets `RUST_TEST_THREADS=1`; `--test-threads 1` says the same).

```sh
# smoke: 12 flows on the smoke grid, split check, standard burns, action-only fees, two edges
cargo test --release --test smoke -- --test-threads 1
# receipt semantics (prints what it observed with --nocapture)
cargo test --release --test semantics -- --test-threads 1
# account lifecycle (likewise)
cargo test --release --test lifecycle -- --test-threads 1
# global contracts (likewise)
cargo test --release --test global -- --test-threads 1
# rules of docs/SEMANTICS.md, by topic (likewise)
cargo test --release --test receipts -- --test-threads 1
cargo test --release --test accounts -- --test-threads 1
cargo test --release --test tokens -- --test-threads 1

# full sweep of every probe flow on the standard grid (0.5-130 Tgas by 0.1, 140-300 by 10;
# 1313 points per flow), JSONL and .meta.json to data/probes/, then the calibration report
cargo run --release --bin calibrate -- --flows flows/probes.toml

# the model side, on ../modules/ (TLC: TLA2TOOLS_JAR or ../tools/tla2tools.jar)
python3 scripts/mkconf.py                 # all flows; or name some
scripts/tlc.sh $(python3 -c 'import tomllib; print(" ".join(f["name"] for f in tomllib.load(open("flows/probes.toml","rb"))["flow"]))')
python3 scripts/conform.py                # per-flow comparison, summary table, exit status
```

A flow passes `conform.py` only if:

- TLC finished without error (the log is read once, so the completion check and the reports
  come from the same run);
- the sweep's `.meta.json` is a JSON object with all of `flows_sha256`, `grid`, `points` and
  `jsonl_sha256` (a missing field fails, so `{}` binds nothing); it names the current
  `flows/probes.toml` and the flow's declared grid, and its `points` and `jsonl_sha256` are those
  of the JSONL beside it;
- the sweep holds every point of that grid exactly once (an empty or truncated sweep fails);
- TLC finds no violation of `NotStuck`: a model branch that has run every step and can do
  nothing more is `Done` (no data or non-yield receipt left over). Such a branch prints no
  report, so without this check another branch at the same point could hide it;
- the model has every grid point and none outside it, and one outcome per point: TLC may print a
  point more than once, and two reports of it that differ in any field (parked yields,
  receiver, method, transaction, id, status, gas) fail the flow;
- every status vector is equal and the edges are identical. A receipt's label is its
  transaction, receiver and method (`tx2:y::resume`): transactions are numbered 1 for the swept
  one, then the `after` calls in order (the sweep's `tx` + 1; the model's `ProbeConf` counts
  only transactions, not `expire` steps), so outcomes swapped between transactions fail. The
  vector also holds the number of yields still parked once the point's last step has run (the
  sweep's `yields`, the model's `Parked`; shown as `parked-yields=N` when not 0);
- at every point the receipts pair up one to one by label and status with attached gas within
  `--tol` (5 Ggas). Status and gas are compared together, so two receipts of one method whose
  statuses and gas are swapped between model and sim fail. Within a (label, status) group the
  sorted gas values are paired in order, which minimises the largest difference. The model's
  log (`rlog`) carries no parent and no order, so receipts are matched by label, not by their
  place in the receipt tree, and the order in which they ran is not compared.

The model runs on the library's defaults, except the fee table's rounding: `mkconf.py` pins
`FeeRounding` to `"nearest"` (the cfg line `FeeRounding <- [NearFees] mc_fee_rounding`, with
`mc_fee_rounding == "nearest"` in the generated module), because the comparison measures accuracy and the
default `"up"` overstates an action-only child's fee by up to 4 Ggas on purpose (under `"up"`
two flows, `ft_storage_again` and `wnear_storage_again`, move their edge from 1.0 to 1.1 Tgas;
`docs/SEMANTICS.md`, N-precision). Token batches are accounted per call (each call of a
batch keyed `<acct>.batch/<shape>#<method>`, the per-call keys above), token methods use their
path keys where `CalibProbes` has them, and the token gas knobs are the library's. Apart from
that pin, the cfg sets only the world: `Contracts` = the four probe accounts with code, the token holders and storage
minimum, and the calibrated tables.

For a quick look, `mkconf.py --grid smoke` runs the model on the smoke grid, and
`conform.py --subset` compares only the points the model has (it says so). Calibrate on the
standard grid only: burns are taken at the top of each flow's grid, but a coarse grid can miss
the narrow windows where a path (a refund, an out-of-gas receiver) shows, and the check that a
merged key's largest burn is seen at the top then has less to go on.

### Regenerating the tables

`--from-data` reuses the last sweep in `data/` (not committed). It refuses a sweep whose
`.meta.json` differs from now in any of: sim rev, nearcore rev, protocol, wasm sha256s, flows
file sha256, grid; or whose JSONL does not match its `.meta.json` (sha256, point count, the grid's
points in order). `--force-data` uses it anyway and records the difference in the header. Drop
`--from-data` to sweep afresh.

```sh
cargo run --release --bin calibrate -- --flows flows/probes.toml --from-data \
  --merge-accts ft_probe,wnear_probe --batch-actions --tla tla/CalibProbes.tla --prefix Probe

cargo run --release --bin calibrate -- --flows flows/probes.toml --from-data \
  --merge-accts ft_probe,wnear_probe --batch-actions \
  --group ft_probe:StdFt:ft --group wnear_probe:StdWNear:wnear \
  --tla ../modules/CalibStd.tla --module CalibStd --notes flows/calibstd.notes
```

The header's `command:` line is the command as run, every option included (home directory as
`~`).

The storage tables (no `data/`: each flow of `flows/storage.toml` runs at every point of its grid,
about 20 s):

```sh
cargo run --release --bin calibrate -- --flows flows/storage.toml --stor --merge-accts ft_probe,wnear_probe \
  --group ft_probe:StdFt:ft --group wnear_probe:StdWNear:wnear \
  --tla ../modules/StorStd.tla --module StorStd --notes flows/storstd.notes

cargo run --release --bin calibrate -- --flows flows/storage.toml --stor --group p:Kv:app \
  --tla ../examples/storage-stake/StorKv.tla --module StorKv --notes flows/storkv.notes
```

## Calibrating your own contract

1. Copy `flows/example.toml`. Set `wasm = "${WASM}"` on your contract.
2. Describe the world: accounts, other contracts, `[[setup]]` calls.
3. Declare the static gas and weight of every call the contract makes (`[[static]]`), and what
   each burn grows with (`[[size]]`).
4. Write one `[[flow]]` per path you want a burn key for.
5. Run it:

```sh
cargo run --release --bin calibrate -- --flows my.toml --wasm path/to/contract.wasm \
  --tla MyCalib.tla --prefix My --params app
```

The template runs as written with `--wasm probes/res/probe.wasm`.

The tool works in three steps:

1. **Split check.** It checks that nearcore's leftover split reproduces from your declared
   statics and weights, for every function-call child at every grid point:
   - a single-call parent's leftover is its attached gas minus its measured use
     (`burnt − exec_fees`), its children's exec fees and statics;
   - a multi-call parent splits per action: the children (taken to come from its last call)
     share that call's gas minus its burn, their exec fees and statics. That burn is not in
     the outcome, so it is inferred at the top of the grid and the prediction checked at every
     other point. The report prints the last call's burn and the earlier calls' burn.
2. **Burns.** It takes each receipt's burn at the top of the grid:
   `gas_burnt − exec_fees − send fees of action-only children` (the creator pays those children's
   send fees out of its own gas: `docs/SEMANTICS.md`, "Who pays action send and exec fees"). Send fees come from the fee
   table: Transfer by the receiver's account kind (named, NEAR-implicit, eth-implicit),
   CreateAccount, DeleteAccount, DeleteKey, Stake. AddKey and the deploy actions depend on
   arguments the outcome does not record; one per receipt is solved from the exec fee the child
   prepaid (full-access key, or base + per byte · n with n whole) and priced from the same
   parameters.
3. **Fit.** For each key it fits `base + per · size` (Ggas, size in the unit of `[[size]]`) as
   an upper envelope: `per` is the least-squares slope rounded to the nearest whole Ggas, and
   `base` the smallest whole Ggas that puts every measured burn at or below the line (with
   one size, the largest burn). Exec fees are rounded up too. So the model never has more gas
   left than nearcore on what was measured; otherwise a receipt that needs a fraction of a
   Ggas more than its prepaid gas succeeds in the model. It prints the spread over all
   successful receipts and, as "max residual", the most the line overstates one burn. Past
   the largest size measured a `per` rounded down understates by up to 0.5 Ggas per size
   unit beyond it: measure the sizes you rely on. This matches the fee table's default
   rounding up (`NearFees.FeeRounding`).

A key that never succeeds (a receipt that always fails, such as a receiver that panics) takes
the burn up to its failure (status `failed`, not out of gas), commented as such: the model
needs it (`OPanicKey`) to tell a panic from running out of gas first. It follows the success
keys' convention: function-call children's send fees are in it, action-only children's are
not, but a failed receipt's children are not in the outcome, so a panic after creating an
action-only child would overstate; the probe panics create none. `--batch-actions` adds, for every
multi-call key `K` (calls m1..mn), per-call keys `K#mi`: the burn of the receipt holding
m1..mi minus that of m1..m(i-1), so the prefixes must be calibrated too. The last call's burn
is checked against the split check's inference.

It writes a table only if every check passed: no split mismatch, no child without a declared
static (such a parent would otherwise go unchecked), every action-only fee priced, every size
read, and, for merged keys, the largest burn seen at the top of a grid. `--allow-partial`
writes it anyway, with the failed checks in a WARNING block in its header.

`--params app` turns that account's keys into `app \o ".method"`. The emitted operator,
`MyGasBurn(app)`, can then be instantiated for any model account name. `--merge-accts a,b`
gives those accounts one key per method, holding the largest burn of any path (which must be
seen at the top of some flow's grid), and one key `method/path` per path a flow's `path` or a
`[[path_rule]]` names, holding the largest burn of that path at any grid point. This is the
token modules' key scheme: they look up `<t>.<method>/<path>` first (`PathKey`,
`modules/Nep145.tla`) and fall back to `<t>.<method>`. In `GasCall`, a
child's static and weights come from a spec-level `[[static]]` (the creating contract's code),
else from the flows' `[[flow.static]]` if they agree (the caller's choice, commented as such). `--accts a,b` restricts the table to those accounts. `--group
acct:Prefix[:param]` emits one parameterized pair of operators per account, with parameter
`param` (default the account's model name).

Burns depend on the contract's code and state. A table describes the wasm whose hash is in its
header. Recalibrate for the deployed build.

## Storage bytes

`--stor` measures, per method and path, what a successful receipt adds to its receiver's
storage: nearcore's `storage_usage` before and after the receipt, which the sim reports per
receipt (`ReceiptOutcome::storage`). Each flow runs at every point of its grid
(`flows/storage.toml` gives every flow the `standard` grid), and the bytes are checked to be
the same at all of them: independent of gas as checked at 1313 gas points per flow, not
assumed. The result is not written to `data/`. Keys are named as burn keys are
(`<acct>.<method>[/<shape>][/<path>]`, the flow's `path` or a `[[path_rule]]`), and `--accts`,
`--params`, `--group` and `--prefix` work as for burns. The table is
`<prefix>StorBytes[(params)]`, `key :> [base |-> b, per |-> p]`, bytes = `b + p * size`, with
the size from `[[stor_size]]` (default 0): `arg_len:<f1>[+<f2>...]` (the byte lengths of
string arguments, e.g. a write's key and value), `predecessor_len` (the caller's id, for a
method that registers its caller) or `arg:<field>` (a number). The header records the same
provenance as a gas table, the flows file's sha256 and every size source.

It writes a table only if:

- every key's successful receipts wrote the same bytes at every gas point of a flow (a key
  whose bytes change with gas is an error, not a line);
- a key with a size source has at least 3 distinct sizes, and all its measurements lie
  exactly on one line with a whole-byte slope, checked in i128 (bytes are counted exactly, so
  a point off the line means a size source that misses something, or two paths under one
  key; two sizes would fit any line, so fewer than 3 is an error, and there is no opt-out);
- a key without a size source is a constant: the same bytes at every observation;
- `base` and `per` fit the emitted range (i32);
- the receipts' changes add up, for every account of the spec, to its `view_account` change
  over the flow (no change goes unattributed);
- no receipt changed another account's storage, and no failed receipt changed any. Both
  checks run on every receipt of every run, conversions, refunds and action-only receipts
  included, before any receipt is set aside from the fit;
- every size was read.

For `--merge-accts` accounts each path gets `method/path`, and the bare `method` key exists
only if all its paths lie on one line: unlike burns, bytes have no "largest" to merge to
(`storage_deposit/new` adds 61 + len(id), `/registered` 0), so a model reads the path key and
a missing one is an `Assert`. Action-only receipts (a refund Transfer, an implicit account's
creation) are reported, not emitted: the library counts those bytes itself. A failed receipt
writes nothing, so a key that never succeeds has no entry.

What a table cannot see is the model's to state: the size (TLC has no string length), and
bytes under state the flows did not set up. Give a contract's first mutating call a `[[setup]]`
(near-sdk writes its `STATE` record then), a flow per path that writes differently (a new
key, an overwrite, a removal), and 3 sizes per sized path. At the pins: `put/new` 40 + key + value, `put/same` 0; a
near-contract-standards registration 61 + len(id), its `storage_unregister` the negative,
transfers and withdrawals 0.

## Flow specs (TOML)

| section | fields |
|---|---|
| `[world]` | `protocol_version` (the sim's; default the pinned nearcore's), `names` (sim id → model name), `keys` (method list of a batch → burn key, e.g. `"near_deposit+ft_transfer" = "batch/DT"`) |
| `[[account]]` | `id`, `near` (whole NEAR) |
| `[[contract]]` | `id`, `wasm` (path relative to the spec, or `${WASM}`), `near`, `init = { method, args }`, `source` (free text for the provenance header) |
| `[[setup]]` | a call run once before every flow: `signer`, `receiver`, `method`, `args` (JSON text or a TOML table), `deposit` (yocto, string), `tgas` (default 300) |
| `[[static]]` | `child = "<receiver>.<method>[+method2...]"`, optional `parent`, `actions = [[static_ggas, weight], ...]` (one per function-call action), or `prepaid_minus_ggas` for a child given the creator's prepaid minus a constant |
| `[[size]]` | `key = "<receiver>.<method>"`, `from = "arg:<field>" \| "result" \| "result_size"`, `div` |
| `[[stor_size]]` | `--stor` only: `key = "<receiver>.<method>"`, `from = "arg_len:<f1>[+<f2>...]" \| "predecessor_len" \| "arg:<field>"`, `div` |
| `[[path_rule]]` | `call = "<receiver>.<method>"`, `log`, `path`, `else`: a receipt of that one call whose logs contain `log` has burn path `path`, otherwise `else` (for a path that changes along a flow's grid, such as a resolver that refunds only when the receiver ran out of gas); a flow's own `path` for the call wins |
| `[[flow]]` | `name`, `about`, `tx` (a call as in `[[setup]]`), `grid` (`standard`, `smoke`, `lo:hi:step` in Tgas), `setup` (extra calls), `size`, `static` (per-flow `[[flow.static]]`), `path` / `path_for` (split one method's burns by an argument, e.g. the FT receiver's `msg`; `path_for` empty: every receipt of the flow), `keys` (like `world.keys`, this flow only: a one-call batch `"ft_transfer" = "batch/T"`), `model_keys` (model side only: burn key → the key `mkconf.py` uses instead, where the sim never completes the model's path), `relay` (a relayer account: the flow's `tx` is signed by its `signer` as a delegate and submitted by `relay`; the model runs it through `SubmitDelegate` / `ExecDelegate`), `after` (below) |

The sweep then re-reads every transaction's outcome, so a yield callback is listed under the transaction that yielded, whichever one resumed it. The model runs the same steps (`ProbeConf`'s `After`), each once nothing can run |

Gas is in Ggas unless a field is named `tgas`. Deposits are yocto strings.

## JSONL schema

`data/<spec stem>/<flow>.jsonl` holds one line per grid point (the flow's transaction and its
`after` transactions, in that order), and `<flow>.meta.json` beside
it the sweep's provenance (sim rev, nearcore tag and rev, protocol, every wasm's sha256, the
flows file and its sha256, the grid and its point count) and the JSONL's own sha256
(`jsonl_sha256`). Once the grid has run, a sweep publishes the pair under an exclusive lock on
`<flow>.lock` (beside it; kept): it deletes the old `.meta.json`, writes the JSONL whole (to a temp
file unique to the write, then a rename), and writes the new `.meta.json` last, with the sha256 of
the bytes it wrote. So an interrupted sweep never leaves a `.meta.json` that vouches for other
data, and two concurrent sweeps of a flow leave one sweep's pair, not one's provenance on the
other's data. `--from-data` reads the pair under a shared lock:

```
{ "flow": str, "gas": prepaid (gas units), "tx_ok": bool, "receipts": [receipt, ...],
  "yields": number of yields still parked once the point's last step has run (Sim::yields) }
```

Each receipt is listed in execution order, transaction by transaction, with each transaction's
conversion first and refunds included:

| field | |
|---|---|
| `tx` | the index of its transaction in the flow: 0 for the swept one, then its `after` calls |
| `id`, `parent` | receipt id, and the id of the receipt or conversion that created it |
| `conversion` | true for the transaction's conversion to its first receipt |
| `receiver`, `predecessor` | account ids |
| `methods`, `actions` | method names of its function calls; every action's kind |
| `args` | the first function call's arguments, if at most 512 bytes |
| `refund` | the refund kind (Debug text) for a refund receipt, else null |
| `callback` | whether it waited on a promise result |
| `attached`, `burnt`, `exec_fees` | attached gas (sum over calls), gas burnt, and the receipt's own exec fees inside `burnt` (receipt creation and each action, prepaid by its creator) (gas units) |
| `deposit` | yocto, as a string |
| `status`, `fail` | `ok` / `oog` / `failed`, and the failure (Debug text) |
| `result_size`, `result` | return value length, and the value if at most 64 bytes |
| `logs`, `block` | logs, block height |

An "edge" is a grid point where the status vector changes. The status vector is the sorted
`tx<n>:receiver::methods=status` of every non-refund receipt (`n` = `tx` + 1), and the
parked-yield count.

## Units in the model

- Gas is in Ggas (1 Tgas = 1000).
- Result sizes (`r.res.sz`) and `GasBurn.per` are per KB (1000 bytes). The measured slopes are
  2.84 Ggas/KB for a callback reading its results and 69.53 Ggas/KB for returning a value. The
  table rounds `per` to whole Ggas (3 and 70), and `base` is then the smallest that puts every
  measured burn at or below the line, so over the sizes measured the line overstates by up to
  17.5 and 47.2 Ggas (the "max residual" in `tla/CalibProbes.tla`), never understates.
- The model counts whole Ggas, so nearcore's remainder rule (the last weighted call gets the
  few gas the floor shares leave) is below conformance resolution here; the split check above
  checks it to the gas, and `examples/weight-split` covers it in the model.
- In `ProbeConf`, 1 NEAR is 1000 model units, and the storage minimum and 1 yocto are both 1.

## Async patterns: joint promises and yield/resume

**Joint promises** (`promise_and(..).then`, `docs/SEMANTICS.md` C6) need no new contract: the
probe's `chain` joins its kids unless `detach`. The model builds the joined callback with the
library's `AndThen` (`ProbeConf`'s `HChain`), and `on_read` sums `ResAt(r, i).sz` over
`NRes(r)`. Every receipt of a joint flow takes the flow's `path` (`path_for` empty), so the
joined creator, which also pays a data receipt per input, and the joint callback, which reads
several results, have keys of their own (`p.chain/<children>/and`, `p.on_read/and`, ...),
apart from the detached chains' keys.

| flow | what it checks |
|---|---|
| `and2_ok` | two inputs, both ok; the joint callback's attached gas (static + weighted share) and the creator's need with two dependencies |
| `and2_fail` | one input panics: it fails alone, the callback still runs once |
| `and2_oog` | one input runs out of gas below its window edge (20.2 Tgas), the other succeeds, the callback runs |
| `and2_order_ff`, `and2_order_fs` | result order: `y.on_order` fails iff its first result is `Failed`, so it fails with the failing input first and succeeds with it second. Reversing the order in the probe model fails both flows at 1176 points |
| `and2_s0` | an input with 0 static and weight 0: nearcore rejects it (`FunctionCallZeroAttachedGas`), the creator fails and no receipt exists |
| `and2_cb0` | a joint callback with 0 gas: the same |
| `and3_mixed` | three inputs, on `q`, `p` and `q` (same- and cross-account dependencies) |

**Yield/resume** (C7) runs on the async probe (`probes/async-probe`, on `y-probe.near`):
`yield_create` yields `on_yield` with a chosen static and weight and stores its data id (and
can resume it in the same call), `resume(bytes)` resumes the stored id from a later transaction
and logs whether the host accepted it, and `on_yield` logs whether it got a payload or timed
out. The `[[path_rule]]`s turn those logs into the keys `y.resume/ok` / `/none` and
`y.on_yield/payload` / `/timeout`; the model picks the same keys by what happens.

| flow | `after` | what it checks |
|---|---|---|
| `yield_resume` | resume | the yield callback runs once, with the gas its creator gave it, and nothing stays parked |
| `yield_timeout` | expire | without a resume it times out, and runs (with `Failed`) |
| `yield_resume_late` | expire, resume | a resume after the timeout sends nothing: in the model a resume of a yield that is no longer pending adds no data, and a flow whose model left data behind would report no point |
| `yield_resume_twice` | resume, resume | the second resume (after the callback ran) sends nothing |
| `yield_self_resume2` | | two resumes in the yielding call itself: one callback |
| `yield_cb_oog` | resume | a yield callback with static 100 Ggas and weight 1 runs out of gas between the creator's edge (1.9 Tgas) and its own (2.1 Tgas) |
| `yield_cb0` | | a yield callback with 0 gas fails the creator (`FunctionCallZeroAttachedGas`), as for any other child, although the yield is stored, not sent |

The model's clock is one tick: `YieldTicks = 1` and `MaxBlk = 1 + Len(After)`, so a yield can
time out only after an `expire` step (a `BlockTick`), and each flow has one outcome per point.
The sim's `expire` advances to the real `expires_at` (200 blocks). The resume's 300 Tgas
transaction is compared too (status and attached gas), as transaction 2 (`expire` is not a
transaction: in `yield_resume_late` the resume is transaction 2 on both sides). The yield
callback is listed under transaction 1, the one that yielded, in the sim and the model alike,
whichever transaction resumed it.

**Sim capabilities used** (near-contract-sim at the pinned rev, `src/sim.rs`):

- `Tx::transact()` returns with a yield still parked (it does not advance to the timeout);
  `Sim::yields()` lists the parked ones (`PendingYield { account_id, data_id, expires_at,
  callback_methods, callback_args, receipt_id, tx }`), leaving out resumed ones.
- A resume is a contract call (`promise_yield_resume`) in a later transaction: no sim API is
  needed. `Tx::submit()` with `Sim::step()` / `Sim::settle()` runs several in one block
  (`tests/semantics.rs`).
- `Sim::expire(&y)`: `advance_to(y.expires_at)` (skipping idle heights) and `settle()`, so the
  timeout fires and the callback runs with `PromiseResult::Failed`; it panics on a yield that
  is no longer parked, so `run_flow` checks `yields()` first. `Sim::advance_to(h)`,
  `set_height(h)` and `step()` move the clock directly.
- `Sim::outcome(tx)` re-read later lists the callback under the transaction that yielded,
  and the yielding receipt's `receipt_ids` name it, so the sweep's parent links (and the split
  check) cover it.

**Not covered by a flow:**

- the deadline's length (200 blocks): the model runs on a one-tick clock;
- the race at the deadline (a resume that runs before the timeout's resume receipt wins): one
  outcome per point leaves no room for it; near-contract-sim's own tests cover it
  (`tests/yields.rs:70-92` at its rev 29e9090);
- what a callback reads (the payload or `Failed`, each joint result): the comparison sees
  statuses and gas, not results; only `on_order` turns the first result into a status;
- the order in which receipts run: a point is compared as a multiset of receipts per
  transaction and a parked-yield count at the end, so a joint callback that ran before its
  last input, or a yield callback before its resume, would look the same. That they run after
  is how the flows are built (each `after` step once the chain is idle) and nearcore reading;
- two resumes that run in one block (both return true, the first payload wins), a resume of
  another account's yield, and the payload limit: `tests/semantics.rs` only. A payload over
  1024 bytes fails the resumer in nearcore and not in the model (`docs/SEMANTICS.md`,
  N-yield-payload), so `mkconf.py` refuses such a flow;
- `promise_yield_create_with_id`, a yield with a deposit, a returned yield and a yield as the
  input of a `.then` or `promise_and`; for joint promises, nested joins, an input that returns a
  promise, one result read by index, the restrictions (no return, no appended action, no
  `refund_to`), and the 128-input limit. The sim tests check all of these, with no model
  comparison (`tests/receipts.rs`, `tests/semantics.rs`), except a yield that is itself the
  input of a `.then` or `promise_and` in the call that yielded.

## Mismatch log

Differences between the model and nearcore found by these flows, and what fixed each. The sim
was not patched, and none is a sim-vs-nearcore divergence: the sim runs nearcore's runtime.
None is open after `356fd7b`; the joint-promise and yield/resume flows found none.

1. **ft_storage_again, wnear_storage_again: edge at 1.0 Tgas in nearcore, 1.1 in the model.**
   `storage_deposit` for a registered account refunds the deposit and burns 553 Ggas;
   registering burns 592. With one key per method the model took 592: at 1.0 Tgas nearcore
   needs 553 + 446 (the refund Transfer's fees) and succeeds, the model needed 592 + 446 and
   ran out of gas. Fixed by the library's path keys (`PathKey`, `1ba96ff`) and the calibrated
   `storage_deposit/registered` and `/new` (from `[[path_rule]]`s on the contract's log).
2. **chain_s0: a function call with 0 attached gas.** nearcore rejects the parent's promise
   (`ActionsValidation(FunctionCallZeroAttachedGas)`): the parent fails and no child exists.
   Fixed by the library's zero-gas check (`ZeroGasKid`, `09b28f5`); the parent's burn (1037
   Ggas) is calibrated from that failure. Its children are function calls, whose send fees
   belong in a burn, so nothing needs subtracting.
3. **ft_call_panic, 8.4-8.6 Tgas.** The receiver runs out of gas before it reaches its panic.
   Fixed by the library's panic labelling (`09b28f5`, made explicit in `1ba96ff`: `OPanicKey`)
   with the panic path's burn, `q.ft_on_transfer/panic` (288 Ggas, the burn up to the failure;
   the receiver creates no children).
4. **Token batches with `ft_transfer_call`: attached gas of `ft_on_transfer`.** nearcore splits
   the leftover per call. The library keyed each call by its standalone burn; in a batch
   `ft_transfer_call` burns 35 Ggas less after `near_deposit` (9-10 after `storage_deposit`),
   so `ft_on_transfer` got up to 38 Ggas too little (`wnear_batch_DC` at `09b28f5`). Fixed by the library's per-call batch keys
   `<acct>.batch/<shape>#<method>`, now the default (`TokBatchPerAction`, `1ba96ff`), with the
   per-call burns `--batch-actions` calibrates.
5. **wnear_batch_D at 6.5 Tgas.** nearcore needs a fraction of a Ggas more than 6500; with burns
   and fees rounded to the nearest Ggas the model needed exactly 6500 and succeeded. Fixed
   here: burns and fees round up.
6. **p.send's burn grows with the receiver id's length** (288-307 Ggas): keyed per receiver.

The method keys (`<t>.storage_deposit`, `<t>.near_deposit`, `<t>.ft_resolve_transfer`) still
hold the largest burn of any path, for a model whose tables lack the path keys.
