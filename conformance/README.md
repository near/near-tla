# near-tla conformance

This crate checks the model in `../modules/` against nearcore. It runs generic probe contracts in
[near-contract-sim](https://github.com/near/near-contract-sim), which executes receipts with
nearcore's own `Runtime::apply`. Each transaction runs at every point of a prepaid-gas grid, and
every receipt is compared with what the model predicts at the same point:

- the receipt status: ok, failed, out of gas, or not created;
- the gas attached to each function call;
- the window edges, i.e. the prepaid values at which the outcome changes.

The crate also has a calibration tool. It measures a contract's burn per method and path, and
writes them as a TLA+ `GasBurn` / `GasCall` table with a provenance header.
`../modules/CalibStd.tla` (standard FT and wNEAR) is generated this way.

This is a standalone crate. It is outside any workspace and CI does not build it, because the sim
is a git dependency.

## Pins

| nearcore | `2.14.0-rc.5`, rev `b7b4737cab46f17a6daa2ed694d7aebbd204363a` (from the sim's lock file, copied to `Cargo.lock`) |
| protocol version | 88 (read from the sim at run time; matches `NearFees.tla`'s `FeeProtocol`) |
| Rust | 1.95.0 (`rust-toolchain.toml`) |
| near-sdk / near-contract-standards | 5.29.1 (probe contracts) |

`calibrate` prints all of these and writes them into every table it emits. It reads the nearcore
pin from `Cargo.lock` and the protocol version from the running sim.

These features are not available at this sim rev: `Config::minimum_stake`, `Tx::gas_windows` and
`Fault::HoldUntil`. Instead of `gas_windows`, the crate sweeps the grid itself, cloning the sim
once per point.

## Setup

### Fetching the sim

near-contract-sim is a private repository, so cargo has to fetch it over git with credentials.
The following works with the GitHub CLI signed in. It passes the token through a credential
helper for one command only, and never writes it to a file or remote URL:

```sh
export CARGO_TARGET_DIR=~/.targets/near-tla   # any directory; one per checkout is fine
CARGO_NET_GIT_FETCH_WITH_CLI=true \
GIT_CONFIG_COUNT=2 \
GIT_CONFIG_KEY_0=credential.helper GIT_CONFIG_VALUE_0= \
GIT_CONFIG_KEY_1=credential.helper \
GIT_CONFIG_VALUE_1='!f() { echo username=x-access-token; echo "password=$(gh auth token)"; }; f' \
cargo fetch
```

After the first fetch, cargo builds offline from its git cache.

### Using a local sim checkout instead

Add this to `Cargo.toml` (do not commit it):

```toml
[patch."https://github.com/near/near-contract-sim"]
near-contract-sim = { path = "../../near-contract-sim" }   # your checkout, at the pinned rev
```

Check that the checkout is at the rev in the table above. The provenance check reads the rev
from `Cargo.lock`, so a patched build at a different rev reports the wrong rev.

### The probe contracts

The `.wasm` files in `probes/res/` are committed with their hashes, so the suite runs without a
wasm toolchain. `probe_wasm` refuses a file whose hash is not in `SHA256SUMS`. To rebuild them:

```sh
cd probes && ./build.sh          # builds, copies to res/, rewrites res/SHA256SUMS
cd probes && ./build.sh --check  # rebuilds and verifies against SHA256SUMS
```

`build.sh` runs `cargo build --target wasm32-unknown-unknown --release` with `--cfg near`, as
`cargo near build` does, and the 1.95.0 default wasm features (bulk memory and sign extension
are fine at protocol 88). It remaps every local path prefix (`--remap-path-prefix`) and strips
symbols (`-C link-arg=-s`), so the build is reproducible and the wasm carries no local paths.
There is no wasm-opt pass.

`--cfg near` matters: without it near-sdk 5.29.1 (through near-sdk-env) uses pure-Rust
fallbacks "not for on-chain use", and `env::panic_str` becomes a bare wasm trap (`unreachable`)
instead of the `panic_utf8` host call. With it, a probe's panic shows its message
(`GuestPanic`), and burns are those of an on-chain build.

## Running

All commands run from `conformance/`, with `CARGO_TARGET_DIR` set as above. Tests run one at a
time (`.cargo/config.toml` sets `RUST_TEST_THREADS=1`; `--test-threads 1` says the same).

```sh
# smoke: 12 flows on the smoke grid, split check, standard burns, action-only fees, two edges
cargo test --release --test smoke -- --test-threads 1
# receipt semantics (prints what it observed with --nocapture)
cargo test --release --test semantics -- --test-threads 1

# full sweep of every probe flow on the standard grid (0.5-130 Tgas by 0.1, 140-300 by 10;
# 1313 points per flow), JSONL and .meta.json to data/probes/, then the calibration report
cargo run --release --bin calibrate -- --flows flows/probes.toml

# the model side, on ../modules/ (TLC: TLA2TOOLS_JAR or ../tools/tla2tools.jar)
python3 scripts/mkconf.py                 # all flows; or name some
scripts/tlc.sh $(python3 -c 'import tomllib; print(" ".join(f["name"] for f in tomllib.load(open("flows/probes.toml","rb"))["flow"]))')
python3 scripts/conform.py                # per-flow comparison, summary table, exit status
```

A flow passes `conform.py` only if TLC finished without error, the sweep's `.meta.json` names the
current `flows/probes.toml`, the model has every grid point, every status vector is equal, the
edges are identical and every attached gas is within `--tol` (5 Ggas).

For a quick look, `mkconf.py --grid smoke` runs the model on the smoke grid, and
`conform.py --subset` compares only the points the model has (it says so). Calibrate on the
standard grid only: burns are taken at the top of each flow's grid, but a coarse grid can miss
the narrow windows where a path (a refund, an out-of-gas receiver) shows, and the check that a
merged key's largest burn is seen at the top then has less to go on.

### Regenerating the tables

`--from-data` reuses the last sweep in `data/` (not committed). It refuses a sweep whose
`.meta.json` differs from now in any of: sim rev, nearcore rev, protocol, wasm sha256s, flows
file sha256, grid. `--force-data` uses it anyway and records the difference in the header. Drop
`--from-data` to sweep afresh.

```sh
cargo run --release --bin calibrate -- --flows flows/probes.toml --from-data \
  --merge-accts ft,wrap --tla tla/CalibProbes.tla --prefix Probe

cargo run --release --bin calibrate -- --flows flows/probes.toml --from-data \
  --merge-accts ft,wrap --group ft:StdFt --group wrap:StdWNear \
  --tla ../modules/CalibStd.tla --module CalibStd --notes flows/calibstd.notes
```

The header's `command:` line is the command as run, every option included (home directory as
`~`).

## Calibrating your own contract

1. Copy `flows/example.toml`. Set `wasm = "${WASM}"` on your contract.
2. Describe the world: accounts, other contracts, `[[setup]]` calls.
3. Declare the static gas and weight of every call the contract makes (`[[static]]`), and what
   each burn grows with (`[[size]]`).
4. Write one `[[flow]]` per path you want a burn key for.
5. Run it:

```sh
cargo run --release --bin calibrate -- --flows my.toml --wasm path/to/contract.wasm \
  --tla MyCalib.tla --prefix My --params app
```

The template runs as written with `--wasm probes/res/probe.wasm`.

The tool works in three steps:

1. **Split check.** It checks that nearcore's leftover split reproduces from your declared
   statics and weights, for every function-call child at every grid point:
   - a single-call parent's leftover is its attached gas minus its measured use
     (`burnt − exec_fees`), its children's exec fees and statics;
   - a multi-call parent splits per action: the children (taken to come from its last call)
     share that call's gas minus its burn, their exec fees and statics. That burn is not in
     the outcome, so it is inferred at the top of the grid and the prediction checked at every
     other point. The report prints the last call's burn and the earlier calls' burn.
2. **Burns.** It takes each receipt's burn at the top of the grid:
   `gas_burnt − exec_fees − send fees of action-only children` (D6). Send fees come from the fee
   table: Transfer by the receiver's account kind (named, NEAR-implicit, eth-implicit),
   CreateAccount, DeleteAccount, DeleteKey, Stake. AddKey and the deploy actions depend on
   arguments the outcome does not record; one per receipt is solved from the exec fee the child
   prepaid (full-access key, or base + per byte · n with n whole) and priced from the same
   parameters.
3. **Fit.** For each key it fits `base + per · size` (Ggas, size in the unit of `[[size]]`). It
   prints the residuals and the spread over all successful receipts.

It writes a table only if every check passed: no split mismatch, no child without a declared
static (such a parent would otherwise go unchecked), every action-only fee priced, every size
read, and, for merged keys, the largest burn seen at the top of a grid. `--allow-partial`
writes it anyway, with the failed checks in a WARNING block in its header.

`--params app` turns that account's keys into `app \o ".method"`. The emitted operator,
`MyGasBurn(app)`, can then be instantiated for any model account name. `--merge-accts a,b`
gives those accounts one key per method, holding the largest burn of any path (which must be
seen at the top of some flow's grid). This is the token modules' key scheme. In `GasCall`, a
child's static and weights come from a spec-level `[[static]]` (the creating contract's code),
else from the flows' `[[flow.static]]` if they agree (the caller's choice, commented as such). `--accts a,b` restricts the table to those accounts. `--group
acct:Prefix` emits one parameterized pair of operators per account.

Burns depend on the contract's code and state. A table describes the wasm whose hash is in its
header. Recalibrate for the deployed build.

## Flow specs (TOML)

| section | fields |
|---|---|
| `[world]` | `protocol_version` (the sim's; default the pinned nearcore's), `names` (sim id → model name), `keys` (method list of a batch → burn key, e.g. `"near_deposit+ft_transfer" = "batch/DT"`) |
| `[[account]]` | `id`, `near` (whole NEAR) |
| `[[contract]]` | `id`, `wasm` (path relative to the spec, or `${WASM}`), `near`, `init = { method, args }`, `source` (free text for the provenance header) |
| `[[setup]]` | a call run once before every flow: `signer`, `receiver`, `method`, `args` (JSON text or a TOML table), `deposit` (yocto, string), `tgas` (default 300) |
| `[[static]]` | `child = "<receiver>.<method>[+method2...]"`, optional `parent`, `actions = [[static_ggas, weight], ...]` (one per function-call action), or `prepaid_minus_ggas` for a child given the creator's prepaid minus a constant |
| `[[size]]` | `key = "<receiver>.<method>"`, `from = "arg:<field>" \| "result" \| "result_size"`, `div` |
| `[[flow]]` | `name`, `about`, `tx` (a call as in `[[setup]]`), `grid` (`standard`, `smoke`, `lo:hi:step` in Tgas), `setup` (extra calls), `size`, `static` (per-flow `[[flow.static]]`), `path` / `path_for` (split one method's burns by an argument, e.g. the FT receiver's `msg`), `keys` (like `world.keys`, this flow only: a one-call batch `"ft_transfer" = "batch/T"`), `model_keys` (model side only: burn key → the key `mkconf.py` uses instead, where the sim never completes the model's path) |

Gas is in Ggas unless a field is named `tgas`. Deposits are yocto strings.

## JSONL schema

`data/<spec stem>/<flow>.jsonl` holds one line per grid point, and `<flow>.meta.json` beside
it the sweep's provenance (sim rev, nearcore tag and rev, protocol, every wasm's sha256, the
flows file and its sha256, the grid and its point count):

```
{ "flow": str, "gas": prepaid (gas units), "tx_ok": bool, "receipts": [receipt, ...] }
```

Each receipt is listed in execution order, with the transaction's conversion first and refunds
included:

| field | |
|---|---|
| `id`, `parent` | receipt id, and the id of the receipt or conversion that created it |
| `conversion` | true for the transaction's conversion to its first receipt |
| `receiver`, `predecessor` | account ids |
| `methods`, `actions` | method names of its function calls; every action's kind |
| `args` | the first function call's arguments, if at most 512 bytes |
| `refund` | the refund kind (Debug text) for a refund receipt, else null |
| `callback` | whether it waited on a promise result |
| `attached`, `burnt`, `exec_fees` | attached gas (sum over calls), gas burnt, and the receipt's own exec fees inside `burnt` (receipt creation and each action, prepaid by its creator) (gas units) |
| `deposit` | yocto, as a string |
| `status`, `fail` | `ok` / `oog` / `failed`, and the failure (Debug text) |
| `result_size`, `result` | return value length, and the value if at most 64 bytes |
| `logs`, `block` | logs, block height |

An "edge" is a grid point where the status vector changes. The status vector is the sorted
`receiver::methods=status` of every non-refund receipt.

## Units in the model

- Gas is in Ggas (1 Tgas = 1000).
- Result sizes (`r.res.sz`) and `GasBurn.per` are per KB (1000 bytes). The measured slopes are
  2.84 Ggas/KB for a callback reading its results and 69.53 Ggas/KB for returning a value. The
  table rounds `per` to whole Ggas (3 and 70), so over 100 KB the rounding is up to about
  16 and 47 Ggas.
- The model counts whole Ggas, so nearcore's remainder rule (the last weighted call gets the
  few gas the floor shares leave) is below conformance resolution here; the split check above
  checks it to the gas, and `examples/weight-split` covers it in the model.
- In `ProbeConf`, 1 NEAR is 1000 model units, and the storage minimum and 1 yocto are both 1.

## Results at the pins

**Calibration** (all 58 probe flows, standard grid, probes built with `--cfg near`):

- **Split check:** 76 662 function-call children, 7 408 of them under multi-call receipts
  (checked per action), 0 mismatches, worst difference 0 gas.
- **Action-only children:** exec fees equal the fee table (named 223.18, eth-implicit 7423.18,
  NEAR-implicit 7524.95 Ggas; `flows/actions.toml` adds AddKey, CreateAccount, DeleteAccount).
- **Multi-call receipts** (burn of the last call / of the earlier calls, Ggas): wNEAR DC
  1545.9 / 608.2, DSC 1545.9 / 1183.0, SC 1571.0 / 590.8; FT SC 1570.7 / 591.4.
- **near-contract-standards 5.29.1, `ft_transfer_call`:** `ft_on_transfer` gets static 0 and the
  leftover by weight 1; `ft_resolve_transfer` static 5 Tgas, weight 0. No reserve and no
  prepaid check: the call fails for lack of gas only when burn + 2 child exec fees + 5 Tgas
  exceeds prepaid (edge at 8.4 Tgas); between 8.4 and 8.8 Tgas the receiver runs out of gas.

**Model conformance:** to be re-run on `../modules/` after the library changes listed in the
mismatch log land; `scripts/conform.py` prints the table.

## Mismatch log

Differences between the model and nearcore found by these flows. The sim was not patched, and
none is a sim-vs-nearcore divergence: the sim runs nearcore's runtime.

1. **chain_s0: a function call with 0 attached gas.** nearcore rejects the parent's promise
   (`ActionsValidation(FunctionCallZeroAttachedGas)`): the parent fails and no child exists.
   The model created the child, which ran out of gas, and the parent succeeded. Library fix in
   progress.
2. **ft_call_panic, 8.4-8.6 Tgas.** The receiver runs out of gas before it reaches its panic
   (`oog`); the model reported `failed` (it checked the error before gas). Label only; the
   revert and refund are the same. Library fix in progress.
3. **Token batches with ft_transfer_call (DC, DSC, SC): attached gas of `ft_on_transfer`.**
   nearcore splits the leftover per function-call action (the last call's gas minus its burn
   and its children's costs; earlier calls' leftover is refunded); the model split the
   receipt's whole leftover. Statuses and edges agree; attached gas differed by up to 180 Tgas.
   The calibrator's per-action check reproduces nearcore exactly (numbers above). Library fix
   in progress.
4. **p.send's burn grows with the receiver id's length** (286-306 Ggas). The send flows now key
   it per receiver (`path`), which removes the 11 Ggas difference an earlier single key gave.
5. **Merged token keys.** The token modules have one burn key per method, so a key whose burn
   depends on the path holds the largest burn, seen at the top of a flow's grid:

   | key | path burns (Ggas) |
   |---|---|
   | `wrap.near_deposit` | 604 registered / 674 registering |
   | `ft.ft_resolve_transfer` | 415 / 855 with a refund |
   | `wrap.ft_resolve_transfer` | 417 / 863 with a refund |
   | `ft.storage_deposit`, `wrap.storage_deposit` | 552 with a refund / 591 |

   Conservative by construction.
